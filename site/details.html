Packages / twist_mux

How it is built, what is proved, and what it costs.

twist_mux picks one of several velocity command sources by priority, freshness and locks. This page describes the Lean version: its structure, its theorems, how it relates to the original C++ node, and how the two compare at run time.

Implementation

The node is split so that every decision is made in Lean and nothing else is.

PartWhereWhat it does

C interfacecore/ROSleanCore/FFI.leanExported wrappers the node calls: build a mux, deliver an input message, deliver a lock message, read the decision.

One function decides

The whole behaviour is step : Config → State → Event → State × Bool. An event is a command arriving on input i at time t, or a value arriving on lock j at time t. The boolean says whether to forward the message that just arrived.

def step (cfg : Config) (st : State) : Event → State × Bool
  | .input i t =>
    if i < cfg.inputs.length then
      let st' := { st with inputStamps := setPad st.inputStamps i t 0 }
      (st', select cfg st' t == some i)
    else (st, false)
  | .lock j value t =>
    if j < cfg.locks.length then
      ({ st with
          lockStamps := setPad st.lockStamps j t 0
          lockValues := setPad st.lockValues j value false }, false)
    else (st, false)

The message body never enters Lean. The shim passes an input index and a clock reading in nanoseconds, and forwards the message unchanged when the answer is true. Time is an integer, so the core has no floating point.

// twist_mux_node.cpp: the whole input callback
[this, i, pub](typename MsgT::ConstSharedPtr msg) {
  if (mux_->on_input(i, now_ns())) {
    pub->publish(*msg);
  }
}

Build and deployment

The model lives in its own Lake package so that building the node never needs Mathlib. Lean is a build-time dependency only: the install tree carries the Lean runtime and can be copied to another machine with ROS 2 Jazzy. A Docker build on ros:jazzy-ros-base compiles everything, runs all tests including the comparison with the original, and produces an image with no Lean toolchain in it.

The node takes the same parameter file, topics and QoS as the original, so switching is a change of package name in a launch file.

Theorems proven

All theorems are in ROSlean/Mux/, with no sorry and only Lean's three standard axioms. "Forwarded" means step returned true for a message on input i at time t. A plain-language guide with links to every statement is in THEOREMS.md.

The decision, in one step

forward_iff is the central result: a message is forwarded if and only if its input is configured with positive priority, no active lock outranks it, and every other live input ranks below it (lower priority, or equal priority and later in the list). The rest of this table is that statement read in one direction at a time. Nothing is assumed about the clock.

The code that runs

The node calls exported wrappers, not step directly. muxForward_after closes that gap: build a mux from the handles the node added, feed it any sequence of events, deliver a message, and the decision the node reads is the model's decision for exactly those handles and events. Companion theorems show the configuration keeps the handles in the order added, clamps priorities to 255, and treats a zero or negative timeout as "never expires".

Correspondence to the original code

The model was written from the upstream C++ source, ros-teleop/twist_mux 4.5.1, not from its documentation. The reading is recorded as sixteen numbered rules in SPEC.md, and each Lean definition cites the rule it implements.

Side by side

The selection loop is a direct transcription. Both start from priority 0 and no selection, scan the inputs in order, and replace the candidate only on a strictly greater priority.

Original, twist_mux.cpp

bool TwistMux::hasPriority(
    const VelocityTopicHandle & twist)
{
  const auto lock_priority = getLockPriority();
  LockTopicHandle::priority_type priority = 0;
  std::string velocity_name = "NULL";

  for (const auto & velocity_h : *velocity_hs_) {
    if (!velocity_h.isMasked(lock_priority)) {
      const auto velocity_priority =
        velocity_h.getPriority();
      if (priority < velocity_priority) {
        priority = velocity_priority;
        velocity_name = velocity_h.getName();
      }
    }
  }
  return twist.getName() == velocity_name;
}

Reading the source also surfaced behaviour the documentation does not mention, all reproduced and stated as theorems: an input with timeout 0 is live from start-up and suppresses lower inputs without ever sending a message; a priority-0 input is never forwarded; an input at priority 255 can never be blocked by a lock.

Performance compared with the original

For the configurations robots use (a handful of inputs, one or two locks, commands at 10 to 1000 Hz) the two nodes are indistinguishable in latency, loss and CPU time. The Lean node uses about 50 MB more memory. The Lean core has one weakness: its cost grows with the square of the number of inputs.

Measured on 2026-11-23 on 4 virtual cores of a 2.3 GHz Xeon, ROS 2 Jazzy with Fast DDS. A shared virtual machine, not a robot computer: compare the columns with each other. Method and raw data are in the benchmark report (pull request 1).

Packages / collision monitor

The collision monitor: what is built, proved, tested and trusted.

The stop and slowdown core of Nav2's nav2_collision_monitor, as a lifecycle node that Nav2 can launch. It is not a drop-in replacement for Nav2's default configuration; what is missing has a page of its own.

Implementation

The split is the same as for twist_mux, with a larger shim. Every decision is made in Lean. The C++ side moves data, talks to TF, and does the floating-point arithmetic that stays outside Lean: the scan's points with their transform, and the multiplication of a slowdown.

C interfacecore/ROSleanCore/CollisionMonitorFFI.leanExported calls: build a monitor from parameters, deliver a lifecycle transition, a scan, a polygon message, a command; read the output.

One function decides

The behaviour is step : Config → State → Event → State × Output. An event is a lifecycle transition, a scan, a polygon message for a zone, or a velocity command. For a command the action demanded is:

def evaluate (cfg : Config) (st : State) (now : Nat) (scanPts : Option (List Coords))
    (zoneVerts : List (Option (List Coords))) : Action :=
  match sourcePoints cfg st now scanPts with
  | none => .stopSource
  | some pts => zonesAction (liveConfig cfg st zoneVerts) pts

sourcePoints is none when the scan source is invalid: no scan, a scan older than the timeout, or no transform for it. zonesAction returns the first triggered stop zone, otherwise the triggered slowdown zone with the smallest ratio, otherwise pass. The action does not depend on the command's velocity.

Numbers cross into Lean as bit patterns. Lean converts timeouts to integer nanoseconds and coordinates to integer millimetres in exact arithmetic, and refuses what it cannot represent. The core returns an action, and the shim applies it to the command:

ActionThe shim publishes
passThe command's three planar components, copied bit for bit.
stopZone k, stopSource0.0 in all components.
slowdown k rEach component multiplied by the double whose bit pattern is r.
velocity withheldNo velocity. The state message and the zone polygons are still published.

Theorems proven

All theorems are in ROSlean/CollisionMonitor/, with no sorry, no native_decide and only Lean's three standard axioms. Unless stated, nothing is assumed about the state, the clock or the configuration. The plain-language guide with every statement is THEOREMS.md.

Stop, sourceThe source is enabled, its timeout is not 0, and no scan is stored, or the stored scan is older than the timeout, or the command carries no usable coordinates for it.evaluate_eq_stopSource_iff

Rounding errs towards "inside"

The core tests points against zones in integer millimetres. Points are truncated toward the origin, circle radii are rounded up plus 1 mm, and polygons get a band of √5 mm around their boundary. circle_safe: a point strictly inside the configured circle is inside the model's circle. For polygons the quantitative half is proved (nearSegment_iff, nearBoundary_of_rounded, contains_of_shim); the topological half of the argument is prose. The zones grow by up to 3.5 mm (circle) or 4.4 mm (polygon); those two figures are tested, not proved.

The code that runs

cm_readBack_after_fast: create a monitor, make any sequence of lifecycle, scan, polygon and command calls, deliver a command: the five numbers the node reads back are the codes of the whole output of step for that command, in the state run reaches on those events from start-up. stepCmdFast_eq: the fast command path that C calls is the same function as step. cm_not_ok_after: a monitor whose configuration was refused answers every command with a stop.

The demo
