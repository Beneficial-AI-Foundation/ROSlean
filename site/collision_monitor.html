Collision monitor

The collision monitor uses one laser scan source and circle or polygon zones. It can pass a velocity command, scale it down, demand zero, or withhold it. Nav2’s lifecycle manager can start and activate it with an edited configuration.

Nav2’s default approach zone must be replaced with a supported zone. In simulation, stop zones blocked Nav2 recovery commands and left the robot stopped in three of six tours. Nav2 setup and limits.

Two of the theorems

The model demands a stop if the scan source is invalid or a stop zone triggers. A missing scan, stale scan, or missing transform makes the source invalid only if it is enabled and its timeout is positive.

theorem evaluate_isStop_iff (cfg : Config) (st : State) (now : Nat)
    (scanPts : Option (List Coords)) (zoneVerts : List (Option (List Coords))) :
    (evaluate cfg st now scanPts zoneVerts).isStop = true ↔
      sourcePoints cfg st now scanPts = none ∨
      ∃ pts, sourcePoints cfg st now scanPts = some pts ∧
        ∃ z ∈ (liveConfig cfg st zoneVerts).zones, z.action = .stop ∧ z.triggered pts = true

If the model returns a velocity action, it is pass, stop, or slowdown with a configured ratio in [0, 1). Pass preserves the three planar components.

theorem no_amplification (cfg : Config) (st : State) (e : Event) (a : Action)
    (h : (step cfg st e).2.velocity = some a) :
    a = .pass ∨ (∃ k, a = .stopZone k) ∨ a = .stopSource ∨
      ∃ k r, a = .slowdown k r ∧ r < F64.one ∧
        ∃ z, cfg.zones[k]? = some z ∧ z.action = .slowdown r

ROSlean/CollisionMonitor/Properties.lean, lines 707 and 940. Checked by Lean with no sorry and only Lean's three standard axioms.

While the demanded velocity stays zero, the monitor withholds velocity after stop_pub_timeout. The trace theorem proves that the last velocity it published was zero. The C++ integration applies slowdown in floating point. Stopping distance also depends on the sensors, transforms, zones, and base.

Tested beside the original

The fixed suites ran 318 core checks and 289 Nav2 checks. In 300 randomized zone cases, all 586 differences in demanded velocity were within the stated bounds and ROSlean was stricter in each. Both nodes matched the reference model in 300 randomized Nav2 cases. With 1,080 readings and two polygons, the median command time was 48.9 µs for ROSlean and 7.2 µs upstream. Test details.

Run on macOS arm64 and, in part, in a Linux arm64 container on the same machine. Not run on x86-64, on Linux on its own hardware, or on a robot.

The demo

In Gazebo, a script drops a box in front of a moving TurtleBot3. The monitor scales the command to 40% in the slowdown zone and demands zero in the stop zone. The robot resumes when the box is removed.

In the Nav2 variant, the lifecycle manager starts the Lean monitor with stop and slowdown zones. The box check passed ten times with ROSlean and four times upstream. One earlier attempt failed during Nav2 startup.

The stop zone also blocks reverse, turn, and recovery commands. Gazebo and Nav2 tutorial.
