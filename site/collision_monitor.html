Collision monitor

Nav2's nav2_collision_monitor sits between Nav2's velocity smoother and the robot's base: it reads a laser scan, and when enough points lie in a configured zone it scales the velocity command down or replaces it by zero. The Lean version covers one laser scan source, circle and polygon zones, and the actions stop and slowdown. It is a lifecycle node with the same parameter format, topics and bond, so Nav2's lifecycle manager can launch it in place of Nav2's own monitor.

It is not a drop-in replacement for Nav2's default configuration. That configuration's only zone uses the approach action, which this node refuses; the zone has to be replaced by a stop zone, and the robot then stops where stock Nav2 would slow down gradually. With Nav2 driving in simulation, that stop held the robot for good in three tours of six. The edit, and everything else that is missing.

Two of the theorems

The node demands a stop for a command if and only if the scan source is invalid (no scan, a scan older than the timeout, or no transform for it) or some stop zone is triggered by the scan's points:

theorem evaluate_isStop_iff (cfg : Config) (st : State) (now : Nat)
    (scanPts : Option (List Coords)) (zoneVerts : List (Option (List Coords))) :
    (evaluate cfg st now scanPts zoneVerts).isStop = true ↔
      sourcePoints cfg st now scanPts = none ∨
      ∃ pts, sourcePoints cfg st now scanPts = some pts ∧
        ∃ z ∈ (liveConfig cfg st zoneVerts).zones, z.action = .stop ∧ z.triggered pts = true

And whatever the node publishes, for whatever event, in whatever state, is the command unchanged, a stop, or a slowdown by the configured ratio of the zone named, a number in [0, 1):

theorem no_amplification (cfg : Config) (st : State) (e : Event) (a : Action)
    (h : (step cfg st e).2.velocity = some a) :
    a = .pass ∨ (∃ k, a = .stopZone k) ∨ a = .stopSource ∨
      ∃ k r, a = .slowdown k r ∧ r < F64.one ∧
        ∃ z, cfg.zones[k]? = some z ∧ z.action = .slowdown r

ROSlean/CollisionMonitor/Properties.lean, lines 707 and 940. Checked by Lean with no sorry and only Lean's three standard axioms.

These are statements about commands, not about physics. A demanded stop is published as zero or, once zero has been published for stop_pub_timeout, not published at all, as in Nav2's monitor; a further theorem, run_withheld_last_published_zero, says that the last velocity the node published is then a zero. That the multiplication of a slowdown does not enlarge the command is IEEE-754 arithmetic in the C++ shim, trusted and not proved. Whether the robot stops in front of an obstacle depends also on the sensor, the zone sizes, the transforms and the base.

Tested beside the original

Both nodes were run on the same messages under a simulated clock. In 318 checks of 73 scenario runs, 289 checks of the Nav2 scenarios, and 600 random cases with 43,748 commands, every difference was one of the numbered differences of the specification, and in none did the original stop or slow where the Lean node did not. Where the two differ, the Lean node's zones are larger by up to 3.5 mm (circle) or 4.4 mm (polygon). A command costs 6 to 9 times the original's processor time in process (49 µs against 7 µs for 1080 readings and two polygon zones) and stays inside a stated budget.

Run on macOS arm64 and, in part, in a Linux arm64 container on the same machine. Not run on x86-64, on Linux on its own hardware, or on a robot.

The demo

In Gazebo a TurtleBot3 drives through an apartment with the mux and the collision monitor in series. A script drops a box in its path; the robot continues at 40 % of its speed while the box is in the slowdown zone, stops when it reaches the stop zone, and drives on when the box is removed. An automated check measures the run against the simulator's ground truth. It shows one head-on approach in simulation.

In a second variant Nav2's own bring-up launches the Lean node in place of its monitor, with a stop zone and a slowdown zone where Nav2's default has its approach zone. The check of the box scenario passed there in ten runs of ten, and in four of four with the original node on the same parameters. One further start, the first in a freshly installed environment, failed because Nav2 itself did not come up.

With Nav2 driving a tour of the apartment through these zones, the robot ended standing for good in three runs of six: two of three with the Lean node, one of three with the original node on the same zones. In a stop zone every command becomes zero, including the turn or the retreat that would clear it and Nav2's recovery behaviours. Stock Nav2 with approach reached 11 places in its one run and did not stand. A stop zone is not a substitute for approach. The tutorial, section 7, has the steps and the numbers.
