Overview / Lessons learned

Lessons learned

Three things the project has shown so far. Each is stated with what supports it and where it stops.

Lesson 1

ROS decision logic can be written in Lean

Two ROS 2 nodes have their decisions made by a Lean function: Twist mux, which chooses between velocity command sources, and the collision monitor, which passes, slows or stops a command depending on a laser scan. Lean compiles the function to C. A C++ layer handles topics, parameters, the clock and, for the monitor, transforms; it makes no decisions.

Both nodes take the original package's parameter file and topics and are started like any ROS 2 node. Each was run beside the original on the same messages.

Lesson 2

A theorem shows what an implementation really does

The natural safety statement for a collision monitor is "whenever a stop is demanded, zero is published". It could not be proved for a model that follows Nav2's monitor, because it is false.

When its output is zero, Nav2's monitor publishes that zero for stop_pub_timeout (one second by default) and then publishes nothing for as long as the output stays zero. The clock starts when the output first becomes zero, whatever the cause. So this sequence is possible:

TimePlanner commandsStop zoneThe monitor publishes
0 to 1 s0 (idle)free0
1 to 5 s0 (idle)freenothing: the timeout has run out
5 s onward0.5 m/sobstaclenothing

A stop is demanded from 5 s on and no zero is published for it. The robot does not move: the commands are withheld, and the last thing the base received was a zero.

This is not a bug. Nav2 documents the behaviour and gives its reasons: other systems can then move the robot out of a near-collision state, and a standing robot can go to sleep. The Lean node does the same.

What is proved instead

  • When a stop is demanded, the node publishes zero or nothing, never a non-zero velocity (stop, run_stop).
  • Whenever a velocity is withheld, the last velocity the node published was a zero (run_withheld_last_published_zero).

Together these keep the robot stopped only under an assumption that is not about the node: the base holds its last command, and nothing else commands it in the meantime.

The full note, with when this matters and what a stronger rule would cost: findings/stop_pub_timeout_theorem.md.

Lesson 3

Stating the guarantees points at places to harden

A specification has to say what the node does for every input, including broken ones. Writing that down for laser scans showed a case in Nav2's monitor where a broken input reads as "no obstacles".

The monitor keeps a reading only if it lies between the scan's range_min and range_max. The two limits come from the message and are not checked. If they are unusable, every reading is dropped, the scan yields no points, and no points means free space: the command passes and nothing is logged.

Scan, with 360 readings inside the stop circleCommand of 0.5 m/s comes out as
limits 0.05 and 30 (a working scan)0.0
range_max is NaN0.5
range_min above range_max0.5
both limits 0, the default when a driver never sets them0.5
no readings at all0.5

Observed on nav2_collision_monitor 1.3.12 (Jazzy). The Lean node follows the original here.

How likely it is: not very. The common lidar drivers we read set sensible limits. The plausible sources are a hand-written driver that fills the readings and forgets the limits, a wrong parameter, or a filter that empties the scan.

Why it is still worth handling. The monitor is the last check before the motors, and the failure is silent: the robot drives normally and its zones never trigger. A narrow check, treating a scan with unusable limits as an invalid source, would make the monitor stop as it already does for a stale scan, and would cost working robots nothing.

The full note, with the code references and the proposed check: findings/nan_values_issue.md. A second note of the same kind, on zone shapes with a NaN corner: findings/polygon_nan_vertex.md.
