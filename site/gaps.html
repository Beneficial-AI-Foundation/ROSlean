Packages / collision monitor

What is missing, and what closing each gap would take.

The ROSlean collision monitor is a gate for velocity commands with stop and slowdown zones. Its decision for each command is a Lean function with machine-checked theorems, and Nav2's lifecycle manager can launch it in place of nav2_collision_monitor. It is not a drop-in replacement for Nav2's default configuration, whose only zone uses the approach action, which this node refuses.

What the node is, and how to read this page

"Upstream" is nav2_collision_monitor of ROS 2 Jazzy, read at commit c704655 (version 1.3.14) and run as binaries 1.3.12 (macOS, RoboStack) and 1.3.14 (Linux, apt). The Lean node covers one laser scan source, circle and polygon zones, and the actions stop and slowdown, as a lifecycle node with a bond, a state topic, transforms from TF with base shift correction, and polygon zones whose shape arrives on a topic. The specification is SPEC.md; rule numbers (R, N), differences (D, ND), trusted parts (T) and assumptions (A) below are its.

The claim is about commands, not physics. The theorems say which velocity the node publishes for the messages it received. They do not say that a robot does not collide: that also depends on the sensor, the zone sizes, the base and the transforms.

Every statement on this page is one of four kinds:

KindMeaningWhere to check it
ProvedA Lean theorem, named here. No sorry, no native_decide, only Lean's three standard axioms.THEOREMS.md, ROSlean/CollisionMonitor/
TestedObserved on running binaries, with the test and its counts named.COMPARISON.md
TrustedNeither proved nor fully tested. Each item has a number T1 to T10.SPEC.md, "Where the velocity is computed"

Where things were run: macOS on arm64 (one Apple M5 Pro), and a Linux arm64 container in Docker on that same Mac. Nothing of the node described here ran on x86-64 or on Linux on its own hardware. One early cloud session ran the tests of the node as it was before the Nav2 extension on Linux x86-64. Every timing figure is from that one Mac.

Sizes of remaining work are estimates. Those marked "SPEC_NAV2" are from SPEC_NAV2.md, section 12, and are relative to all collision monitor work so far: the model and its C interface (1,900 lines of Lean in core/), the proofs (8,900 lines in ROSlean/CollisionMonitor/), the C++ shim (2,000 lines) and their tests. Those marked "this page" were made when this page was written and are in no other document.

Under Nav2: what has to be edited

nav2_bringup's nav2_params.yaml configures the monitor with one zone, FootprintApproach, with action_type: approach (SPEC.md, N21). The Lean node refuses that zone. The documented edit replaces it by the footprint as a fixed stop polygon (SPEC_NAV2.md, section 8.6):

polygons: ["FootprintStop"]
FootprintStop:
  type: "polygon"
  points: "[[0.22, 0.22], [0.22, -0.22], [-0.22, -0.22], [-0.22, 0.22]]"
  action_type: "stop"
  min_points: 6

The coordinates are an example. How far the polygon must reach beyond the robot is the user's choice; nothing in this repository relates a zone size to a braking distance. In the launch file, package='nav2_collision_monitor' becomes package='roslean_collision_monitor'; the executable name, the node name, the lifecycle manager's list, the topics and the bond stay.

Changing only action_type of Nav2's zone to stop does not configure, on upstream either: a stop zone does not read footprint_topic, so it has no shape and no topic. Seen on upstream's binary (UPSTREAM_BEHAVIOUR.md, finding 35; scenarios footprint-edit-stop, footprint-edit-slowdown). Adding polygon_sub_topic: "/local_costmap/published_footprint" makes it configure on both nodes, with two limits listed under zone shapes that change.

Tested Nav2's own navigation_launch.py with the package name changed and nav2_params.yaml with the edit above: Nav2's lifecycle manager configured, activated and bonded the node, as a stand-alone process and as a component in component_container_isolated; a command passed, became zero with twenty readings at 0.15 m, and passed again (review CM5, macOS; static transforms and a scripted scan, no simulator, no localisation, no goal). For Nav2 with a simulated robot in Gazebo, see the collision monitor tutorial.

The robot then behaves differently from stock Nav2: it stops when the zone is occupied, where stock Nav2 slows down in proportion to the time before a predicted collision. In a stop zone every command becomes zero, including backing up and turning, as with upstream's stop action.

Actions

approach

Slows the robot so that it keeps a set time before a predicted collision with its own footprint.

Upstream
CollisionMonitor::processApproach in src/collision_monitor_node.cpp, Polygon::getCollisionTime in src/polygon.cpp, src/kinematics.cpp. The robot's motion is simulated in steps of simulation_time_step up to time_before_collision, with cos and sin of the turned angle; at each step the points inside the footprint are counted; the command is scaled by collision_time / time_before_collision. The footprint comes through nav2_costmap_2d::FootprintSubscriber.
Nav2's default
Yes. It is the only zone of nav2_params.yaml. The package's own example file defines such a zone but does not list it.
This node today
Refuses. The configure transition fails, the node stays unconfigured, the process stays up. The log says:
1 parameter refused: parameter 'FootprintApproach.action_type': only 'stop' and 'slowdown' are supported; got 'approach'. (To use Nav2's footprint zone, give it 'points', or 'action_type: stop' together with 'polygon_sub_topic'; 'footprint_topic' is read for 'approach' only.)
To close it
Model: the simulation loop over a rotating and translating point set, in exact arithmetic, with cos and sin supplied by the shim or enclosed in rational bounds. To prove: the scale factor is in [0, 1]; no amplification; if the unscaled command reaches min_points points within the horizon, the published speed is at most the scaled one. Would stay trusted: cos, sin, one division, unless the rational bounds are proved, which is a project of its own. The shim also needs the footprint subscriber's pose lookup.
Size (estimate)
The largest single item: about half of all collision monitor work so far (SPEC_NAV2).

limit

Caps the linear and angular speed while a zone is occupied.

Upstream
processStopSlowdownLimit in src/collision_monitor_node.cpp: ratio = min(1, linear_limit / hypot(vx, vy), angular_limit / |w|), clamped to [0, 1], applied to all three components.
Nav2's default
No. The package's example file defines PolygonLimit but does not list it.
This node today
Refuses, with the message above and got 'limit'.
To close it
A new action kind. The ratio needs a square root and a division: computed by the shim and checked in Lean on bit patterns (the check's premises stay trusted), or compared in squares exactly. To prove: no amplification; the published speeds respect both limits up to rounding.
Size (estimate)
About a tenth of the work so far (SPEC_NAV2).

A polygon whose shape arrives on a topic: provided, with four limits

This is how Nav2's footprint can become a zone (polygon_sub_topic). The node has it (N29 to N35). What a user should know:

No shape yet
Until its first accepted message the zone takes no action; a stop zone does not stop. Upstream's behaviour (N32), kept by the user's decision; fail-open. Proved not_triggered_of_no_shape, output_of_no_shape. The node warns about it when configured.
Left behind
A footprint from the costmap is in the odom frame. Between two costmap updates the zone lags by the distance driven; if the costmap stops publishing, the robot drives out of its zone (N34; seen on upstream, scenario footprint-sub-topic). Kept as upstream by the user's decision. The fixed polygon has neither problem, which is why it is the documented edit.
Unusable vertex
After a polygon message with a vertex that is not finite or lies more than 999.997 m from an axis, the zone demands its action for every command until a usable message arrives or the node is cleaned up (ND6). Upstream takes such a message as it is, and its zone then catches some points and misses others. More restrictive than upstream. Proved triggered_unusable_of_triggered, evaluate_isStop_of_unusable, run_stop_after_unusable. Decided, not confirmed a default the user has not confirmed.
Refused refresh
If the recomputed vertices of a zone in another frame are not finite or out of range, the zone stays where it was for that command (ND13, refresh_of_refused). This needs the zone's frame about a kilometre from the base. It is the one place where the node can in principle let a command pass that upstream would stop. Open for the user.

Proofs not done

What is proved is listed on the details page. This section lists what the theorems rest on without proving it. The numbers T1 to T10 are SPEC.md's trusted list.

The topological half of the polygon margin argument

The model's polygon zones are grown by a band of √5 mm so that rounding to integer millimetres never loses a point that the configured polygon contains.

Proved
The quantitative half. The band test is exactly "at most √5 mm from the segment" (nearSegment_iff). A point of the real polygon's boundary is, after rounding, within the band (nearBoundary_of_rounded; with room for the shim's floating-point transform, contains_of_shim, contains_of_shim_fixed). A point upstream's rule puts inside the rounded polygon is counted (contains_polygon_iff). For circles the whole claim is proved (circle_safe, circle_safe_shim).
Not proved
That one of the two cases always applies: if the real point is inside the real polygon and the rounded point is outside the rounded polygon, then the boundary passed over the point during rounding. This is prose in SPEC.md. Also not proved: the figures in the other direction (a point up to 3.5 mm outside a circle or 4.4 mm outside a polygon can count as inside).
Tested instead
band_bounds: 34.0 million points against upstream's own zone tests on 340 zones, on macOS and in the Linux container: upstream never counted a point the core did not, and the farthest point outside upstream's zone that the core counted was 3.409 mm for a circle and 4.167 mm for a polygon. Random comparison of the two nodes: below, under stricter or looser.
To close it
A definition of upstream's crossing rule over the real numbers, and a continuity argument: the parity of crossings cannot change while the point stays off the boundary. Neither is in the repository.
Size (estimate)
About the size of the existing geometry proofs, Geometry.lean (700 lines), or more (this page).

The floating-point multiplication of a slowdown (T1)

The Lean core never multiplies. For a slowdown it returns the ratio's bit pattern and the shim computes command × ratio in double.

Proved
A published slowdown carries the configured ratio of the zone named, with its sign bit clear and a value in [0, 1) (no_amplification, published_ratio_in_unit_interval, lt_one_iff), and that ratio is at most that of every triggered slowdown zone (slowdown_bound).
Trusted
That the IEEE-754 product of a finite double with a double in [0, 1) has the same sign or is zero, has magnitude at most the original, and does not grow when the ratio shrinks. "The published speed is at most the commanded one" is therefore a Lean theorem plus T1.
To close it
Multiply in the core on bit patterns (a correctly rounded binary64 product in integer arithmetic, about fifty lines by SPEC.md's count) and return the output bits; then prove no amplification for that function. SPEC.md calls the proof a project of its own.
Size (estimate)
About the size of the existing conversion proofs, Convert.lean and Bits.lean together (700 lines) (this page).

The transform code, and the points a command carries (T2, T6, T7)

The C++ shim computes each scan point in the scan's frame, looks the transform up in TF, applies it in double, and hands Lean one coordinate pair per reading with every command.

Proved
What the model does with whatever coordinates it is given. The number of points is the number of valid readings of the stored scan (points_length); each point is the pair it was given, truncated toward the origin by less than 1 mm (coordMm_eq_truncReal, scanPointMm_sub_lt); a missing transform stops when source_timeout is not 0 (no_transform, run_no_transform).
Trusted
That pair i is the image of reading i of the stored scan (T2); cos, sin and the angle accumulation in float (T2); tf2's tree, interpolation and product, and that the shim asks for the right frames and times (T6); the node's own waiting loop and its clearing of the TF buffer at a backward clock jump (T6); that upstream's point is within 0.04 mm of the shim's, estimated at 10⁻⁸ mm (T7). All of it is in one file, transforms.hpp (260 lines).
Tested instead
smoke_transforms: on 200,000 transforms the shim's points equal, bit for bit, a reference written out operation by operation; the object code contains no fused multiply-add. The scenarios tf-* and shift-* of scenario_nav2.py beside upstream. A mutation test of the review caught 9 of 11 changes to the transform code, one was equivalent, and the one it missed has a test since.
Decided
By the user: the transform is applied in C++ as upstream applies it (option A), compiled with -ffp-contract=off on every platform. An earlier version applied it in Lean in exact arithmetic and proved every scan point to be the exact image of its reading; it cost about 20 times upstream's time per command and was replaced.
To close it
Either restore the exact transform in Lean and make it fast enough, or prove the floating-point formula against a formal model of binary64 arithmetic, which this repository does not have. tf2 itself would stay trusted in both.
Size (estimate)
The first: the model and its proofs were built once (task T05) and removed, so restoring them is known work; making them fast enough is not estimated. The second: not estimated (this page).

The IEEE-754 reading of bit patterns (T4)

The core compares and classifies floating-point numbers as bit patterns, without floating-point arithmetic.

Proved
Against a formula written in this repository for the number a pattern denotes (magVal): the comparison of ranges is ≤ on the denoted numbers and false for NaN (le_iff_value); which reading is valid (validBeam_iff_value); patterns are ordered as their magnitudes (magVal_strictMono).
Trusted
That the formula is IEEE-754's; that the compiler's float and double are binary32 and binary64; that upstream's own <=, isfinite and == 0.0 are the IEEE operations.
Tested instead
review/collision_monitor/Checks.lean compares the helpers with the hardware operations on some 300,000 patterns each, with no disagreement.
To close it
Prove the formula equal to an independent formalisation of IEEE-754. None is in the repository or its dependencies as used here.
Size (estimate)
Not estimated: it depends on the formalisation chosen.

Decisions, and the behaviour each implies

A demanded stop is not always published

This is not a defect. Upstream does it on purpose and documents it, and the user decided to keep it. It is here because it is the reason one theorem is weaker than one would expect.

When the node's output is zero it publishes that zero for stop_pub_timeout and then publishes nothing for as long as the output stays zero (R15; upstream: publishVelocity). The clock starts when the output changes from non-zero to zero, and the rule looks at the value, not at its cause.

TimePlanner commandsZoneNode publishes
0 to 1 s0 (idle)free0
1 to 5 s0 (idle)freenothing: the timeout has run out
5 s onward0.5 m/sobstacle in the stop zonenothing

A stop is demanded from 5 s on and not one zero is published for it. The robot does not move: the 0.5 m/s commands are withheld, and the last message the base received was a zero. The sequence is an example in Examples.lean, checked by decide; upstream behaves the same in the scenarios stop-publication and zero-input.

StatementStatus
"Whenever a stop is demanded, zero is published."False, for upstream and for this node. Not claimed.
When a stop is demanded, the node publishes zero or nothing, never a non-zero velocity.Proved stop, run_stop
In any run from start-up, when a velocity is withheld, the last velocity this node published was a zero.Proved run_withheld_last_published_zero

The two proved statements keep the robot stopped only under assumption A3: the base holds its last command, and nothing else commands it in the meantime. It matters when another node publishes to the base during the silence (teleop, a recovery behaviour, docking), which upstream intends to allow; when the base needs fresh zeros to stay stopped; or when something reads "no zeros" as "no stop". The state topic does report the stop.

To close it: publish zero for every command that meets a demanded stop, without a time limit. "A demanded stop is published" then becomes a theorem and A3 is no longer needed for stops. The cost is a deliberate difference from upstream: an outside system can no longer take over the velocity topic while the obstacle is in the stop zone and the planner is still commanding, and the comparison tests must leave these cases out. A parameter with upstream's behaviour as the default would keep both. Size (estimate, this page): one condition in the model's step, and the theorems about stop_pub_timeout in Trace.lean and Properties.lean restated; small beside the items above. The full note is findings/stop_pub_timeout_theorem.md.

Stricter or looser than upstream

Every difference from upstream has a number. For a safety gate the direction matters.

DirectionDifference
More restrictiveD3, D4: zones are grown, by up to 3.5 mm (circle) or 4.4 mm (polygon), and all boundary points are inside. ND6: an unusable polygon message makes its zone demand its action. D15: zero for every command while the clock is invalid, where upstream's process ends. D6: a slowdown is applied to commands so small or large that upstream's test under- or overflows and passes them unslowed. ND4: silent after shutdown, where upstream keeps forwarding. D5, D9, D10: negative slowdown ratios, negative or non-finite timeouts, max_points and out-of-range min_points are refused.
Later, same decisionND3: a stop by an earlier zone can be published later than upstream publishes it, by up to transform_tolerance for each later topic zone whose transform lookup fails. Read from source, not run.
Less restrictive, in principleND13 only: a refused refresh leaves a topic zone where it was, which misses points a kilometre away that upstream's moved zone would catch.
Not comparableD8: a scan with a negative stamp ends upstream's process. This node takes the stamp as 0; while the node clock is still below source_timeout such a scan counts as fresh.
Fail-open, kept as upstreamA topic zone with no shape yet (N32); source_timeout: 0 (R8, N27); scans with unusable limits or no valid reading read as free space (R4); a disabled source (R6); a footprint zone left behind (N34); no output without commands (R1); silence after stop_pub_timeout (R15).

Tested On the final node, macOS, beside upstream 1.3.12: 318 checks in 73 scenario runs and 289 checks in 44 runs of the Nav2 extension, 0 failures, every difference one of the numbered ones (D1 1, D4 20, D5 3, D6 1, D8 1, D9 2, D10 2; ND4 2, ND5 1, ND6 4, ND11 3). 300 random cases with 26,951 commands: none outside the bounds of D4; 586 commands with a different demanded velocity, each decided by a point in a growth band (farthest 2.056 mm outside a circle, 3.044 mm outside a polygon), the Lean node the more restrictive one every time. 300 random cases of the extension with 16,797 commands: both nodes gave the model's answer to every one. In the Linux arm64 container: the 289 checks, and 20 random cases with 1,182 commands, with the same result. No case was found in which upstream stops or slows and the Lean node does not, outside ND13, which no test produces.

Not generated by either random test: a polygon message with a non-finite vertex, a backward clock jump, a wait for a transform. Those are covered by scenarios only.

Cost

The node costs more processor time per command than upstream and stays inside a stated budget. Both are true.

Median per command, the callback bodies of both nodes in one process on the same messages, nothing in a zone, the identity as the transform and no TF buffer; one Apple M5, macOS arm64 (task T06). That is 6 to 9 times upstream's. In the Linux arm64 container an earlier version of the command path measured 4.2 to 6.4 times upstream's (task T03); the final node was not timed there. The budget is a line drawn in this project (150 µs is 0.75 % of the 20 ms between two commands at 50 Hz), not upstream's speed; the test roslean_cmd_cost asserts it for the Lean core alone.

Not measured: a transform from the TF buffer in the loop, base shift correction, topic zones, any x86-64 machine. Through the two node binaries over topics at 50 commands a second, both answered every command; the median latency, most of it the measuring program's and the middleware's, was 5.8, 6.7 and 7.5 ms for the Lean node and 6.3, 6.6 and 6.4 ms for upstream at 360, 1080 and 10,000 readings (macOS).

Whether upstream's speed is wanted is the user's to say; until then the budget is the target (tasks/PLAN.md). The scan callback costs about 10 ns per reading, where upstream stores a pointer.
