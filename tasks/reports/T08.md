**Verdict.** The Lean node answers every scenario and 600 random cases as
upstream does up to the stated differences, and Nav2's own launch file and
lifecycle manager run it; but it lets a command pass where upstream stops
when a zone's polygon message has a NaN vertex, and under simulated time it
hangs when the clock jumps back while a command waits for a transform.

**The orchestrator's points.**

- **a (exceptions caught in `main`; the component).** Nothing found that is
  swallowed and should stop the robot. The only exception found leaving a
  callback is rclcpp's on a negative `/clock`; under simulated time the
  catch makes the clock invalid, so commands are stopped until a usable
  `/clock`; on the wall clock it is only logged. A command whose callback
  throws gets no answer at all; no throwing statement was found between the
  core's call and the publication (from source). As a component a negative
  `/clock` ends the container, for upstream's component too (from source,
  not run). SIGINT during a wait: both nodes end with SIGSEGV (observed).
- **b (the wait loop).** Finding 2. Otherwise as upstream: boundary,
  arrival during the wait, tolerance 0, timeout 0 (T07's scenarios, run
  here); real time uses the node clock as tf2 does (from source); nothing
  but `/clock` is handled inside the wait, so Lean sees no event from
  inside it (observed, `wait-reentrancy`). From source, not run: the TF
  buffer is not cleared during a wait, and the start of each lookup's wait
  differs in which clock reading it takes.
- **c (`stepNoClock`).** Finding 4, with the precise statement: guaranteed
  are the no-clock theorems, every one-step theorem and every "from any
  state" trace theorem on the segments without such commands; not
  guaranteed by any theorem in the repository is anything stated from
  `State.init` after the first processed no-clock command. Proved in the
  review file: the mixed run agrees with `run` on the list in which each
  processed no-clock command is `deactivate, activate`, except for one
  report. A no-clock command is silent unless the node is active and the
  command finite; it publishes a stop even where R15 would withhold.
- **d (reading i and coordinate i).** No break found: one thread, scan and
  core updated in one callback, the model ignores a scan only when
  finalized, shapes kept exactly when accepted (from source and Lean).
- **e (the 32 checks).** All 32 are state messages, none a velocity: 18 at
  checks with a stated velocity difference (D4 16, D6 1, D8 1), 14 at the
  check after one (D4 13, D6 1). Stated differences, not defects.
  `STATE_TOPIC` left `False`: the profile's format cannot state them.
- **f (cleanup).** Nothing observable carried or lost: the model after
  cleanup is `State.init` but for the unread `stopStamp` (Lean); upstream
  keeps only its toggle and stop stamp (from source). The shim keeps the
  clock's validity and its last `/clock` reading.
- **g (mutations).** 17 of 19 caught, one missed (finding 6), one
  equivalent.
- **h (Gazebo).** `pixi run cm-check` passed in 75 s.
- **i (threads).** Finding 5.

## Found wrong or changed

Nothing was changed in the node, the model, the SPEC or the tests. Found
wrong: the six findings above. In the authors' reports:

- T06, item 8: "32 of 318 checks failed, 29 of them state messages … and 3
  the new D4 entries". On the merged tree all 32 are state messages.
- T06, item 1, and SPEC_NAV2 8.3: the node's loop is described as tf2's
  rule; it lacks tf2's third condition (finding 2).
- SPEC_NAV2 ND6 and N33: the reason given for refusing a NaN vertex is
  false (finding 1); `polygon-topic` tests the one arrangement where it
  holds.
- THEOREMS.md, "End to end": "there is no prefix to add" holds only without
  no-clock commands (finding 4).

## Questions for the user

1. **Finding 1.** What should a topic zone do after a message with a
   non-finite (or out-of-range) vertex: stop until a usable message arrives
   (never less restrictive than upstream), or reproduce upstream's
   arithmetic on NaN? Keeping ND6 as it is means documenting that upstream
   can stop where this node passes.
2. **Finding 2.** Add tf2's rule to the node's loop (smallest change), or
   give rclcpp its clock thread back and call tf2 (T06's question 2)? With
   the first, the TF buffer still is not cleared during a wait.
3. **Finding 4.** Should T09 take `mixed_from_init` into the repository, or
   make the no-clock command a constructor of `Event` after all?
4. **Finding 3a/3b.** As upstream (publish only enabled zones; fall back
   to the topic), or record them as differences?
5. **The component.** With a negative `/clock` it dies with its container,
   as upstream's does. Is "as upstream" enough for the component, with D15
   promised for the executable only?
6. **State messages in the old scenarios.** Extend the profile's format, or
   leave the comparison to `scenario_nav2.py` and `random_nav2.py` (which
   compare them, without boundary cases)?

## Friction

- The worktree guard refuses a shell command that names `git` next to
  anything else, or a path it cannot verify; clones had to go under the
  session's scratch directory, and commits are one command each.
- macOS has no `timeout`; long runs got a watchdog in the script.
- `colcon`'s `setup.bash` reads unset variables, so a script with `set -u`
  dies at once (cost one restart of the random run).
- The session's scratch directory is shared with earlier tasks: a
  directory named `runs` already held T02's logs.
- Both nodes publish a zone's polygon on the same topic when run side by
  side; to tell them apart one of them has to be stopped.
