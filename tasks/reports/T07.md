## Done

1. **The harness** (`test/cm_harness.py`) gained: a `/tf` publisher with
   chosen stamps (`publish_dynamic`), transforms with any translation and
   quaternion (`xf`), static transforms sent while the node runs, a
   `PolygonStamped` publisher per `polygon_sub_topic` (reliable, volatile or
   latched), recording of polygon topics (`Side.polys`), `get_state`, and the
   node's endpoints on a topic with their QoS (`endpoints_of`). Nothing that
   `scenario.py` and `random_diff.py` use was changed.
2. **`test/scenario_nav2.py`**, 37 fixed scenarios in six families, each
   expectation an output observed from upstream here. New kinds of step:
   lifecycle transitions inside a scenario (with what they must and must not
   publish), `/tf` and `/tf_static` messages, shapes, `arrives` (the missing
   data comes while a command waits), the polygons a step must publish
   (frame, stamp, points), the node's subscriptions and publishers and their
   QoS, its lifecycle state, and text in its output. The node is an
   argument; `--profile` as in `scenario.py`; `--only` takes family names;
   `--first-failure`. Parameters: `test/zones_nav2.yaml`, and for the
   footprint family `nav2_bringup`'s `nav2_params.yaml` and the package's
   `collision_monitor_params.yaml` as installed, edited in memory.

## Not run, and why

- **The ROSlean node through any of it**, beyond the first check: it has no
  lifecycle interface yet (T06). The three `roslean_nav2_*` tests are
  expected failures.
- **`pixi run test`**: by the rule. **`pixi run test-quick` and every
  test registered before this task**: on the orchestrator's instruction
  (above). So that `cm_harness.py` still serves `scenario.py`,
  `random_diff.py` and `fault_injection.py` rests on the change being
  additive (new functions and one new attribute), not on a run.
- **Linux on Linux hardware, x86-64, the cloud**: the Linux runs are a
  container on the Mac. In it the five scenarios that edit `nav2_params.yaml`
  and the lifecycle-manager half of `bond_manager.py` were not run: the
  image has neither `nav2_bringup` nor `nav2_lifecycle_manager`. So the
  refusal of Nav2's edited zone is observed on Linux for the package's
  example file only.
- **Not covered by a scenario**: the point markers (N17; the ROSlean node
  does not provide them, ND9); `~/toggle` and that it survives cleanup (ND8);
  the real local costmap as the publisher of the footprint (the messages
  are the harness's); the component form of the node; `autostart_node`;
  the bond under simulated time; a zone circle fed by a topic (N36); base
  shift correction after a backward clock jump (inferred in finding 37, not
  run); transforms with inexact quaternions at a zone boundary (excluded by
  T05b's note).
- **ND7** (a non-finite or zero quaternion): `tf-bad-quaternion` shows that
  tf2 does not take such a transform, so the ROSlean node's own check cannot
  be reached through a scenario.
- **Not covered by the random test**: the wait of N26 (`transform_tolerance`
  is 0 there), tf2's interpolation, points within 5 mm of a zone boundary,
  backward clock jumps, shutdown, non-finite shapes, polygon topics (only
  velocities and state messages are compared).
- **Expectations for the ROSlean node that depend on where the transform is
  applied** (ND1, ND3, and D3/D4 at boundaries after a transform): not
  stated, on the orchestrator's instruction. `shift-interpolation` is the
  one new scenario with points exactly on a zone boundary; it pins
  upstream's interpolation and the profile leaves it out for the ROSlean
  node.

## Found wrong or changed

Verified by a run unless marked "inferred".

**Upstream against SPEC_NAV2.md: no contradiction.** Every row of the test
plan came out as the document says. What the binary showed beyond it (each
is in SPEC_NAV2.md 10.1 and UPSTREAM_BEHAVIOUR.md now):

- **N28, made more precise.** SPEC_NAV2.md says a backward clock jump
  "clears the TF buffer" [S]. On the binary the transforms received on `/tf`
  are forgotten and those from `/tf_static` are not. Reproduce:
  `scenario_nav2.py --only tf-clock-jump-back` (the node logs `Detected jump
  back in time. Clearing TF buffer.`; a scan in the static frame still
  stops by the zone; a scan in the `/tf` frame waits and gets `invalid
  source` until the transform is sent again). Inferred, not run: with
  `base_shift_correction: true` every command after a backward jump is held
  for `transform_tolerance` and then stopped until odometry stamped at or
  after the new clock arrives.
- **N8.** Shut down from `active`, the node not only forwards: it still
  takes scans and publishes stops and state messages
  (`lifecycle-shutdown-active`). Shut down from `inactive` it is silent.
- **N15** (was "[S only]"): a zone named `invalid source` hides the change
  to an invalid source on the state topic (`state-name-collision`).
- **N26.** `transform_tolerance: 1.001` is 1,001,000,000 ns (rounded to
  nearest; `source_timeout: 1.001` is 1,000,999,999 ns), observed to the
  nanosecond (`tf-tolerance-decimal`, `tf-tolerance-0.3`).
- **N27.** With `source_timeout: 0` a command whose lookup fails passes, but
  only after the wait (`tf-wait-timeout0`).
- **N24.** tf2's interpolation between odom samples decides a zone boundary
  exactly for binary fractions (`shift-interpolation`), on both platforms.
- **N23.** A transform with a newer stamp is used by the very next command.
- **N25.** A zero quaternion, a NaN in the quaternion and a NaN translation
  are refused by tf2 on entry (`tf-bad-quaternion`).

**In the harness, found and fixed during the task:** the first clock
message of a scenario could be sent to nobody. All scenarios use the node
name `collision_monitor`; while the previous scenario's process was still
in the graph, "the node has subscribed to `/clock`" was true of the old
process. Seen twice as `polygon stamped 0, the node clock is 100000000000`
in `polygon-pub` (the only scenario whose first step is a clock message
followed by nothing that takes time). The runner now waits until the old
endpoints have left the graph before it starts the node. That this was the
cause is inferred; after the change the scenario passed in every run (see
"Run").

**In the random test, seen once:** in the first colcon run seed 9 of
`upstream_nav2_random` disagreed with the model at two commands with 50 ms
between events and agreed on the retry with 300 ms; the test passed. T02
reports the same kind of event for `random_diff.py`.

**In `tasks/T07-nav2-harness.md`:** nothing wrong. Item 6's "including the
base moving away from it without a new message (N34)" is
`footprint-sub-topic`.

## Questions for the user

1. **A backward clock jump.** Upstream then forgets every transform it got
   from `/tf`; with base shift correction (Nav2's default) that means
   stops for `invalid source` until new odometry arrives. If T06's shim uses
   `tf2_ros::Buffer` as upstream does, the ROSlean node inherits this. Keep
   as upstream (the default by PLAN.md's rule), and list it among the things
   the documentation does not say?
2. **`upstream_nav2_bond`** takes 21 s, runs on the wall clock and is in
   `test-quick`. Leave it there, or label it `long`?
3. **Linux image.** `bench/cm_linux/Dockerfile` installs neither
   `ros-jazzy-nav2-bringup` nor `ros-jazzy-nav2-lifecycle-manager`. Should
   T08 add them (not a file of this task beyond `run.sh`), so that the
   footprint scenarios and the manager test run on Linux too?

## Friction

- The session's worktree guard refused any shell command that combined
  `git` with other commands or contained a long heredoc; commits, pushes and
  larger document edits had to be separate plain calls.
- Under simulated time a node that waits inside a callback looks exactly
  like a node that lost a message. Two scenarios were first written with a
  clock that ran backwards by mistake (the TF buffer was cleared and
  everything after it waited); that mistake is how finding 37 was found.
- All scenarios share one node name, so the ROS graph of the previous
  scenario leaks into the next for a moment (above).
- `WILL_FAIL` cannot say why a test fails; the three expected failures
  print one distinctive line, quoted in the CMakeLists.
- The Linux image predates this task: the test directory is mounted over
  the image's copy rather than rebuilding 6.5 GB.
