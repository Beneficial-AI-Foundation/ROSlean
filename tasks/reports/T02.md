## Found wrong or changed

Verified by a run unless marked "inferred". Full account in
`docs/collision_monitor/COMPARISON.md`, section "Defects".

**In the Lean core (model): a command is slow; with T05's exact transform in Lean (option B, being replaced by T05b) very slow.** All figures "after T05" below are option B and must be repeated after T05b and T06. Each command
places every stored reading again (`Scan.points`, `Xform.pointMm`, exact
arithmetic) before the zones are tested.

- Reproduction without ROS: `build/roslean_collision_monitor/cmd_cost`.
  1080 stored readings, two polygon zones: 3.2 ms per command back to back
  and 7.6 ms with one command every 20 ms on macOS; 2.5 ms and 6.8 ms in the
  Linux container. Before T05 (commit `91c21f9`): 0.41 ms and 1.7 ms on
  macOS. Upstream: 8 to 12 µs.
- Through the nodes, 1080 readings, scans at 25 Hz, commands at 50 Hz
  (`run_cm_bench.py node`): in the Linux container the Lean node's
  median latency is 5.8 ms, upstream's 0.26 ms (before T05: 2.4 ms against
  0.37 ms). With 10,000 readings a command takes 24 to 29 ms, longer than
  the 20 ms between commands, and the Lean node answers 532 (macOS) and 678
  (Linux) of 1000 commands where upstream answers 850. At scene changes 9
  answers differed from upstream's in four runs; for the 2 whose direction
  was recorded the Lean node was the more restrictive. The opposite
  direction (the Lean node still passing while upstream already stops,
  because the obstacle's scan waits behind a long command callback) follows
  from the same delay; it was not observed, and the run meant to count it
  was stopped. **Inference, not measurement.**
- Registered: `roslean_cmd_cost`, `WILL_FAIL` (asserts 25 ns per reading and
  zone; prints 1,160 to 1,480 ns).
- That the placement is where the time goes is inferred: the cost per
  reading is nearly the same for circles and polygons (2.5 and 2.9 µs),
  where before T05 it was 16 and 380 ns, and the source shows the placement
  in the command path. It was not profiled.
- The task brief of T03 describes this defect with the numbers of the first
  draft (200 ns per reading and zone, polygons only). They are now seven
  times larger for polygons and 150 times larger for circles.

**In the node (as in upstream): a `/clock` message with a negative time
ends the process.** `terminating due to uncaught exception of type
std::runtime_error: cannot store a negative time point in rclcpp::Time`,
signal 6, on both platforms; upstream's binary dies with the same message.

- Reproduction: `ros2 topic pub --once /clock rosgraph_msgs/msg/Clock
  "{clock: {sec: -5}}"` at a node started with `-p use_sim_time:=true`; or
  `fault_injection.py NODE --only clock-negative` (prints `FAIL  the node
  has exited with code -6`, `2 failure(s) in 3 checks`).
- Registered: `roslean_fault_clock_negative`, `WILL_FAIL`.
- That the exception is thrown in rclcpp's clock thread is inferred from
  rclcpp's design, not inspected.

**Fixed by T01, re-measured:** the unoptimised build of the shim
(`CMAKE_BUILD_TYPE` is `Release` on both platforms) and the one-bit
difference of scan points on macOS (node and upstream's library both import
`___sincosf_stret`; `t2_point_as_upstream` passes and is no longer marked
`WILL_FAIL`).

**In the harness, fixed here:**

- `IndexError` in `scenario.py` after `wait_connected` (T01's report):
  `wait_connected` now requires its conditions before and after its half
  second of spinning, and the endpoint lists are read by a function that
  waits and reports a failed check instead of raising. The crash was seen
  once by T01 and never here (more than a thousand scenario runs), so the
  cause, a publisher counted and then gone, is inferred from the code.
- A refusal passed whatever its reason. Now the node's message must name
  the one parameter the profile states (12 checks; `roslean_scenario` has
  318 checks instead of 306).
- The random comparison allowed the Lean node a micrometre beyond the
  bounds of D4 (`LEAN_SLACK`); now 0. All 720 seeds pass without it on both
  platforms.
- `cm_load` counted answers that differ between the two nodes without their
  direction; it now counts "first node less restrictive" and the reverse.
- The fault tests used `ROS_DOMAIN_ID` 97 and 98; now 120 and 121.

**In the documents:** COMPARISON.md rewritten where its numbers changed;
its section on defects now has "open", "fixed since the first draft" and
"found in the harness". The WIP commit's changes to SPEC.md ("Note on
testing against upstream") and UPSTREAM_BEHAVIOUR.md (finding 16) were kept
as they were; the statements in them were re-checked by the probes on both
versions of upstream.

**Not a defect of this repository, seen once:** the twist_mux test
`scenario` failed in a `pixi run test-quick` made while sixteen other test
processes were running: upstream's `twist_mux` dropped one message
("key (90) passes the watchdog lock (50)"), the Lean mux did not.
Run again on the final tree with the machine quieter, it passed (58 s).

## Questions for the user

1. **The cost of a command.** Decided in part while this task ran: the
   transform moves to C++ (option A), which removes the 2.5 µs per reading
   that T05 added. What remains open is the cost before T05, which option A
   returns to: 0.4 ms per command hot, 1.7 ms paced, 2.4 ms median through
   the nodes against upstream's 0.4 ms (1080 readings, two polygons). Is
   that acceptable, or is T03 item 2 still wanted? And should T05b/T06 be
   required to pass `roslean_cmd_cost` or a budget before they merge?
2. **The limit of `roslean_cmd_cost`**, 25 ns per reading and zone back to
   back: an arbitrary line (three times the circle path before T05, several
   times upstream's whole cost). Is that the target T03 should meet, or is
   there a budget per command (for example 0.2 ms at 1080 readings)?
3. **Negative `/clock`.** Upstream aborts in the same way. Keep it as a
   defect to fix (T03 item 1), or accept it as "as upstream" and record it
   in the SPEC?
4. **`docs/REVIEWS.md`.** The WIP commit had added a section "CM comparison"
   there. The file is not this task's, the merge conflicted, and
   `collision-monitor`'s version was taken. Should a short entry pointing to
   COMPARISON.md be added by whoever owns the file?
5. **A Linux computer.** The latency through the nodes is the one
   measurement where the platform decides what is seen (10 ms middleware
   tick on macOS, 0.3 ms in the container). Is a run on real Linux hardware
   (the cloud machine of T00, x86-64) wanted before the write-up, T11?
6. **The twist_mux scenario test** failed once in `pixi run test-quick`
   while 16 other test processes were running (upstream's `twist_mux`
   dropped one message; the Lean mux did not). Not a file of this task; is
   a retry inside that test wanted, as the collision-monitor harness has?

## Friction

- **The integration branch moved under the task.** T05 was merged into
  `collision-monitor` while the measurements were running, and it rewrote the
  core. Everything had to be run twice. The second set of runs is the one
  that found the largest defect, so it was worth it, but a task that
  measures "the node as now on `collision-monitor`" needs either a frozen
  commit named in its brief or a note that it must re-check the branch
  before it writes numbers down.
- **Time.** One pass of the comparison on one platform is about 75 minutes
  of machine time even with the random seeds in eight processes: 25 minutes
  random, 5 scenarios, 25 in-process latency (since T05; 2 before), 35
  soak, 20 the package's tests. Most of it is waiting on real nodes in real
  time.
- **`WILL_FAIL` cannot say why a test fails.** A harness error makes an
  expected failure "pass". The two such tests print one distinctive line;
  COMPARISON.md and the CMakeLists quote them.
- **Docker.** `docker/Dockerfile` has no `nav2_collision_monitor` and throws
  the build tree away, so a second Dockerfile was needed (`bench/cm_linux/`).
  The repository's `.dockerignore` does not exclude `core/.lake`, which on a
  Mac holds macOS objects; the new Dockerfile has its own ignore file.
- **macOS has no `timeout` command**; long commands were given the tool's
  own limit instead.
- **Buffered output.** `scenario.py` writes nothing to a redirected log
  until Python flushes; `PYTHONUNBUFFERED=1` is needed to watch a run.
- **Parallel runs.** Sixteen test processes at once (eight per platform)
  work, each on its own `ROS_DOMAIN_ID`; one random case and one twist_mux
  scenario needed a retry or failed under that load.
