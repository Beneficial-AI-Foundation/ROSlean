## Found wrong or changed

Nothing was changed outside the task's files. No build or test failed on
Linux. Three things in the repository do not fit the cloud:

1. `tasks/README.md` (before this task) and `pixi run prove` tell a session
   to run `lake exe cache get`. Here that command neither works nor fails
   quickly: about 30 files a minute, each a 403, 9133 files. Reproduce:
   `lake exe cache get` in a fresh checkout. The README now says not to run
   it; `pixi.toml` is outside this task.
2. `check_demo.py` does not notice that Gazebo has exited. With the world
   failing to load (`[INFO] [gazebo-1]: process has finished cleanly`,
   `process[gazebo-1] was required: shutting down launched system`) it kept
   waiting at "waiting for the robot to drive straight with free space
   ahead" until killed after 300 s; with Gazebo segfaulting it reported
   failure only after 380 s. Reproduce: `pixi run cm-check` here.
3. `apartment.sdf` cannot be loaded without `fuel.gazebosim.org`, so no
   Gazebo run is possible in the cloud with the world as committed.

## Questions for the user

1. The network policy of the cloud environment blocks `cache.mathlib.org`.
   Allowing it would turn 35 minutes of `lake build` per session into a
   download of a few minutes. Allowing `fuel.gazebosim.org` would let the
   Gazebo check run on the committed world (under Xvfb). Allowing
   `releases.lean-lang.org` and `pixi.sh` would make the fallbacks in the
   script unnecessary. Should the policy be changed, or should the tasks
   plan for the 35 minutes?
2. If `fuel.gazebosim.org` stays blocked: should a later task add a world
   without furniture (or a switch in the launch file) so that
   `pixi run cm-check` can run in the cloud? T00 may not change those files.
3. The branch name (top of this report): is `claude/cloud-setup-task-egn5jr`
   acceptable in place of `claude/t00-cloud-setup`?

## Friction

- Finding out that the Mathlib cache was the problem cost ten minutes: the
  command prints one failure line per file and keeps going.
- elan's error for the blocked host is a Rust backtrace; the cause
  (`CONNECT tunnel failed, response 403`) is one line in the middle.
- The machine has no `zstd`, so Lean's `.tar.zst` release could not be
  unpacked; the `.zip` (1 GB instead of 660 MB) could.
- A script cannot set the caller's `PATH`; every new shell needs the
  `export` line.
