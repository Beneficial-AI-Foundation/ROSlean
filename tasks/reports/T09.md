**What was read for finding 5** (verified by disassembling `libleanrt.a` of
the pinned toolchain, 4.37.0-rc1, macOS arm64): `lean_initialize_thread` is
a branch to `lean::initialize_thread()`, which calls `getenv` and `strtol`
and stores a number, nothing else; `lean_finalize_thread` is a single
`ret`. The build is with mimalloc (`LEAN_MIMALLOC` in `lean/config.h`).
Neither function is declared in `lean.h`. So the call has no effect here; it
is made because Lean's documentation requires it and a toolchain with Lean's
small-object allocator needs it. **Not checked:** the Linux toolchain's
`libleanrt.a`. **Still trusted** (SPEC.md, T10): that no two threads are
inside the core at once; the wrappers do not mark objects as shared.

## Found wrong or changed

- **In the review's text** (finding 3b): "`points` that does not parse to
  four pairs". Upstream's rule is "more than three points, each a pair"
  (`getPolygonFromString`); five points are fine. N29 says it that way.
- **In T08's and T04's N28**: the TF buffer is cleared *when the `/clock`
  message arrives*, during a wait too (verified on upstream by
  `tf-wait-clock-back`). T08 had it from source, not run.
- **In the node, found while fixing finding 2** (not a finding of the
  review): after the change the clock a shape message's wait ended with
  would have been used as the stamp of the polygons published at the next
  activation (display only, and only if a shape message waited and no
  command came in between). It was in the binary of the first runs of the
  new scenarios and of the Linux image; fixed (`waited_until_ns_.reset()` in
  `on_shape`) before the runs reported below as "final tree". No test shows
  it either way.
- **Pre-existing, not changed, from source:** when a callback starts,
  rclcpp's clock and the node's own `/clock` subscription can be one message
  apart. If the node's subscription already holds a later message than
  rclcpp has processed, the first reading of a wait is that later time, and
  a wait can end sooner than upstream's by the gap between two `/clock`
  messages. Not reachable on the wall clock; under simulated time it would
  show as a stop for `invalid source` one clock tick early. No scenario
  shows it.
- **ND13 is not in the safe direction in every case** and the report of the
  review did not say so: for points about a kilometre from the base
  upstream's moved zone can catch what this node's unmoved zone does not.
  Recorded in the row; not changed.
- `mixed_from_init` is on the model's states. It is **not** lifted to the
  exported functions (`Call` has no no-clock command), so "End to end" for
  sequences with no-clock commands is prose on top of two theorems, and
  THEOREMS.md says so.

## Questions for the user

1. **Finding 1, the default that was never confirmed.** After a polygon
   message with a NaN or out-of-range vertex a topic zone now demands its
   action until a usable message arrives. This is what PLAN.md says; it
   makes the node stop where upstream sometimes passes. Confirm, or choose:
   reproduce upstream's arithmetic on NaN (not possible in integers without
   a rule for it), or ignore the message as before and document that
   upstream can stop where the node passes.
2. **A slowdown zone with the mark slows down, it does not stop.** That is
   "the zone demands its action". Should a marked zone stop whatever its
   action? It would be a second rule, easy to add.
3. **ND13** (a refresh that cannot be taken leaves the zone where it was)
   was recorded, not changed. Should a zone whose refreshed vertices are
   unusable also demand its action, like ND6? It needs a base about a
   kilometre from the zone's frame, and it is the one place left where the
   node can in principle be less restrictive than upstream.
4. **ND3's delay** (3d) is documented, not removed. Removing it needs the
   core to say, between the scan's lookup and the zones' lookups, which
   zones the decision can still depend on: a second call per command. Worth
   it?
5. **The TF buffer has a clock of its own now**, and the node clears it on a
   backward jump. This matches upstream in every scenario, but the clearing
   is the node's code instead of tf2's (trusted, T6 c). The alternative
   (the node's clock, tf2's hook) clears a second time after a waiting
   callback and forgets transforms upstream keeps. Is the choice right?
6. **Mixed runs are not lifted to the C interface** (finding 4). Is the
   statement on the model's states enough, or should `Call` get a no-clock
   constructor so that `cm_readBack_after` covers it?

## Friction

- The worktree guard refuses any shell command it cannot verify: a command
  with a variable as its first word, `git` beside other commands, a long
  heredoc. Patches went through script files written with the Write tool;
  that cost about twenty refused commands.
- macOS has no `timeout`; a two-line `perl -e 'alarm …; exec'` wrapper did.
- colcon installs with symlinks, so a rebuild changes the binary under a
  running test. The random comparisons had to be stopped and started again
  after the last rebuild; an interrupted `random_nav2.py` leaves its node
  processes behind (eight here, removed by PID).
- A third field in `TopicShape` broke only what constructs one by position
  (four examples); the proofs needed changes in seven statements. The fast
  path needed none, because it is stated on `Config.withShapes`.
